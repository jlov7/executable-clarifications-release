# Usage

The installed `executable-clarifications` command and `python -m executable_clarifications.cli` have the same interface. With no arguments, inspect the packaged reviewed age-window grid and the first question. Repeat `--answer true`, `--answer false` or `--answer neither` in question order. Every invocation reconstructs the session from the grid and that answer sequence; it does not load browser storage or silently resume a previous run.

`--target module:function --export-test new_file.py` writes a unittest for your separate function. Both options are required together. The parent directory must exist, and existing files are refused. The command emits JSON on stdout, with the replayable record under `session`. Redirect stdout to retain that record. Errors use exit code 2; success uses 0. Execution is a separate operator action under normal Python authority. A narrowed set is not a verified specification, and an OPEN session can export its already recorded examples.

For a different reviewed grid, use `--grid grid.json` with exactly this envelope:

```json
{
  "generator_input": {
    "schema": "executable-clarifications/integer-grid-v1",
    "field": "days",
    "operators": ["<", "<="],
    "thresholds": [20, 30]
  },
  "domain": [19, 20, 21, 29, 30, 31]
}
```

The file limit is 65536 bytes. There are 2..64 predicates, 1..1000 domain integers and at most 64 recorded answers. Portable integers are within `[-(2**53 - 1), 2**53 - 1]`. Only `<`, `<=`, `>`, `>=`, `==`, `!=` are accepted. Boolean, float, missing, string and container field values are unknown in predicate evaluation; they are invalid session-domain values. The grid accepts no labels, requirement prose or code.

The API follows the same path: `generate_candidates(grid)` then `Session(candidates, domain)`, `question()`, `answer(question_id, bool_or_none)` and `render_contract(session, 'implementation:decide')`. `Session.from_record(record)` replays and checks the specification digest and question identities. The digest detects drift; it does not authenticate authorship.

The browser is a source-only demonstration served by `scripts/serve_session_demo.py` at `127.0.0.1`. It provides three fixed authored scenario trees and downloadable records, assumptions and implementation contracts. Completion displays the surviving rules and the recorded input/output answers. Neither stops the tree and blocks assertion export. Undo returns to the preceding question and updates the record and exported contract; Reset clears all answers. To supply your own grid, use the CLI above. The browser does not accept custom grids or requirements prose. Download a supplied integer example session and import it through the policy/session picker to restore its exact state and undo history. Other integer grids remain a CLI/Python path. No data is sent off the machine.

The legacy `core.render_test` remains an internal bounded-candidate demonstration used by older tests. It reconstructs its own predicate and cannot test a separate implementation. Use `session.render_contract` for implementation regression contracts.


## Custom policy format

`--policy` and the browser file picker accept `executable-clarifications/policy-v1`. The complete [refund sample](../src/executable_clarifications/resources/refund_policy.json) is included in the wheel and source archive. Its `fields` declares `days: "integer"`, `unopened: "boolean"` and `reason: {"enum": ["changed mind", "defective"]}`. Each `candidates` entry has only a unique `id` and a `rule`. Each `cases` entry has only a unique `id` and an `input` object containing every declared field.

A leaf predicate has exactly `field`, `op`, and `value`. Operators are `==`, `!=`, `<`, `<=`, `>`, `>=`, and `in`. Ordering is integer-only; `in` takes 1..32 unique values of the declared field type. A group is exactly `{"and": [predicate, predicate]}` or `{"or": [predicate, predicate]}` and supports 2..16 children. For free shipping, use an OR group with `total >= 50` and `member == true`. No requirements prose, intended-label table or executable code is accepted.

Limits: 1..16 typed fields, 2..32 reviewed candidates, 1..256 concrete cases, 128 predicate nodes and depth 6 per candidate. Policy JSON nesting is at most 16. The versioned session envelope permits one additional level (17); its embedded policy is still validated at 16. A policy is at most 131072 canonical UTF-8 bytes; an imported JSON file/session is at most 262144 bytes. Integers are within `[-(2**53-1), 2**53-1]`. Decimal/exponent numeric syntax, floats, booleans as integers, null, missing and unknown fields are rejected. Enum strings are 1..64 ASCII letters, digits, spaces, underscores, periods or hyphens. IDs are 1..64 portable ASCII identifiers allowing a trailing hyphen. Duplicate object keys, duplicate IDs, duplicate enum/membership values, prototype-related keys, markup and unknown schema fields are rejected.

Python and JavaScript validate the same versioned format and evaluate it independently. Cross-runtime tests compare every refund answer path, specification SHA-256, question identity, replay and exact exported contract bytes. These tests are parity evidence for the supported vocabulary, not a proof for every future change. Candidates/cases are sorted by ID. Question choice balances surviving candidates, breaking ties by case ID. The version digest binds the normalized reviewed specification; changing a case, rule or field rejects an old saved history. A digest is not an authenticity signature. A coherent rewritten session can still be authored by anyone.

An ordinary adaptive session still uses `executable-clarifications/policy-session-v1`, with unchanged policy, digest, ordered decisions and exact contract bytes. The first explicit case label upgrades that session to `policy-session-v2`. Its `actions` preserve the exact order of adaptive answers, independent labels and explicitly reconfirmed labels. Replaying either version checks all identities, answer types, action fields and the digest. Maximum v2 actions: 288. Both session envelopes permit depth 17; embedded policy-v1 remains bounded at 16. Saved records use compact JSON within the unchanged 262144-byte import limit.

The browser's typed editor emits policy-v1 and supports all existing field types, predicates, membership and nested AND/OR groups. Changing a field type resets candidate rules for explicit review. Invalid drafts remain visible but cannot be activated or downloaded. Applying an unchanged draft preserves the current answers and labels. JSON preview/import/export remains available without requiring JSON editing. Structural comparisons factor only byte-identical subtrees at corresponding tree positions; they make no semantic equivalence claim. Full rules remain expandable.

The all-cases view displays each case's asked/unasked status and every candidate prediction. Only an adaptive boolean answer or an explicit label becomes an assertion. Choosing a label that no candidate predicts yields `NO_CANDIDATE_MATCH`, but its observed example still exports. Neither remains unresolved and blocks export. Undo removes the latest action. The Python APIs are `case_review()`, `label_case(case_id, bool)`, `revision_preview(policy)` and `reconfirm(original_record, case_id)`; existing adaptive APIs are unchanged. The CLI resumes either record version; interactive case labels and revision previews are provided by the browser/API.

Returned policy session records, questions, case reviews, observed examples and revision previews are detached snapshots in Python and JavaScript. Editing those returned objects does not edit the session; use its answer, label and revision operations. In the policy editor, adding a candidate or case chooses an unused generated ID after deletions or imports and preserves surviving rows.

Editing the current policy opens an explicit revision preview while preserving the original session. It identifies added, removed or modified rules/cases and field changes. Old observed answers are pending review, not assertions in the new session. Start the revision empty, then explicitly reconfirm unchanged inputs or provide fresh answers. A changed or removed input cannot be reconfirmed. The preview and original remain in page memory and the original can be downloaded independently. Closing the page loses the preview; retain both sessions as local files. A reconfirmed action records the old digest as provenance, not an authenticity signature or proof of a reviewer. Coherently rewritten records remain possible.

## Finite semantic policy impact

Use `--policy BASELINE.json --compare-policy PROPOSED.json`, or replace `--policy` with a custom-policy `--resume`. The read-only `policy_impact` result compares all candidates sharing a stable ID, including candidates eliminated from the current session. Added and removed IDs are reported separately. Both policies must use the same field names/types and enum value sets; enum ordering may differ. Incompatible vocabularies yield explicit field definitions and no output comparison. No coercion, case migration, reconfirmation or candidate selection occurs.

Python provides `compare_policies(baseline, proposed, observed_case_ids=())` in `executable_clarifications.impact` and `PolicySession.compare_policy(proposed)`. JavaScript provides `PolicyEngine.comparePolicies(baseline, proposed, observedCaseIds=[])` and `session.comparePolicy(proposed)`. Optional observed IDs must be distinct baseline case IDs. Session methods derive them from explicit recorded answers. `revision_preview()`/`revisionPreview()` includes the same report as `impact`; the existing browser revision preview displays it before starting an empty session. Witnesses remain unlabelled, including when an old recorded input exercises a change.

Report schema: `executable-clarifications/policy-impact-v1`. Per aligned candidate, `false_to_true_count` and `true_to_false_count` count distinct checked inputs with changed outputs. Their `observed_` and `unobserved_` components distinguish recorded baseline example inputs from changes those examples miss. Duplicate supplied inputs count once. Status is `changed-on-checked-inputs` or `unchanged-on-checked-inputs`, never universal equivalence. Observed expected booleans do not determine these counts or supply new labels.

The deterministic domain collects integer literals (including membership values) and supplied case values from **both** revisions, then includes each safe integer neighbor at offsets -1/0/+1. Booleans use false/true; enums use all declared values in sorted order. Fields omitted from every rule still participate. A per-field cap retains all supplied values and the lowest remaining derived values, with exact eligible/retained/omitted value counts. Supplied inputs from baseline then proposed are checked first, followed by Cartesian combinations in sorted field/value order; duplicates are skipped. Thus finite-domain completeness covers only the disclosed retained values. Other integers and intent remain unverified.

Limits: 1024 retained values per field, 5120 input-generation attempts, 4096 distinct checked inputs, 128 representative witnesses and 1048576 canonical UTF-8 report bytes. Each witness is the first encountered input for a candidate, change direction and observed/unobserved status. `coverage` gives exact domains, domain counts, attempt count, decimal-string total/checked/omitted combinations, completeness flags and stop reasons. `output` gives emitted-report byte count, omitted changed candidate/input pairs and the sampling/byte limit reason. Sample omission is distinct from omitted grid coverage. Existing policy/session/case limits and assertion export stay unchanged.

Try `examples/access-baseline.json` against `examples/access-proposed.json`. The baseline's ordinary cases do not exercise the exclusive-boundary edit or trainee exception; finite comparison supplies concrete changed inputs for review. This is authored software evidence. A human still decides intended outputs; human usefulness, productivity and independent intent validation remain NOT RUN.

## Boundary and exception case suggestions

For a custom policy, choose **Suggest boundary and exception cases** in the all-cases view. The preview lists newly generated inputs without labels and shows how many old answers need review. **Apply suggested cases** opens the existing revision workflow; it does not copy answers into the new digest. The original session remains downloadable. Cancel preserves it unchanged. Suggestions remain available when candidates all agree or only one survives.

Python `suggest_cases(policy)` or `PolicySession.suggest_cases()` and JavaScript `PolicyEngine.suggestCases(policy)` or `session.suggestCases()` return the same `{policy, added_cases, coverage}` JSON. The policy is still policy-v1; added entries contain only `id` and `input`. Every candidate and existing case stays intact. Generated inputs are deduplicated against existing inputs and each other, with collision-free `suggested_0001` IDs. They receive no operator label. The `coverage` object records attempts, limits, truncation and its stop reason, unreferenced fields and the scope of the enumeration.

The preview reports every field domain and exact total, covered and omitted combination counts as decimal strings. Coverage counts distinct inputs, including existing cases, rather than case IDs. For grids of at most 4096 combinations, the deterministic order is the Cartesian product of sorted field names and sorted typed values. Larger grids first prioritize single-field then two-field changes from sorted seed-case IDs, followed by that Cartesian order. Integer values include each seed/rule literal and its portable neighbors; membership integer literals count too. Boolean fields use false/true, and categorical fields use all declared alternatives. The procedure never uses predictions, observed labels or surviving-candidate votes. It stops after 4096 attempted variations, at 256 total cases, or before exceeding 131072 policy bytes. Existing byte/depth/type limits still apply. The preview states truncation explicitly. All multi-field interactions in the reported finite grid are included when bounds permit. `finite_domain_complete` means every combination of those reported values is present, even when existing case IDs duplicate inputs. A stopped pass reports omitted combinations and its limiting reason. It does not mean every integer, undeclared field, exception or user intention has been covered. Repeating suggestions uses the newly reviewed cases as seeds and can propose further neighbors.

The CLI accepts `--suggest-cases` with `--policy` or a custom `--resume`; `--export-policy NEW.json` optionally writes its unlabeled policy. The active session and saved answers stay on the original digest. Import the exported policy to start an empty revision. `--label-case ID=true` or `ID=false` explicitly records a label, after any adaptive `--answer` options; it can repeat. Reusing an answered ID fails and requires undo first. All outputs refuse existing paths. CLI reconfirmation is available through the Python revision API or browser, not implicit label copying. A directly authored unittest table remains a simpler baseline when the cases and expected outputs are already known.


## Known example sets

This is separate from policy-v1 and policy sessions. An example set supplies truth directly, without candidates, question selection, extra labels or a finite grid:

```json
{"schema":"executable-clarifications/example-set-v1","fields":{"days":"integer","urgent":"boolean","kind":{"enum":["ordinary","blocked"]}},"examples":[{"id":"boundary","input":{"days":30,"urgent":false,"kind":"ordinary"},"expected":true},{"id":"exception","input":{"days":47,"urgent":true,"kind":"ordinary"},"expected":true}]}
```

Only `schema`, `fields` and `examples` are accepted. There are 1..16 fields and 1..256 explicitly supplied rows, each with exactly `id`, `input` and a boolean `expected`. Every input supplies exactly the declared fields. The portable identifier, integer and enum vocabulary matches custom policies: safe integers within `[-(2**53-1), 2**53-1]`, booleans, or 1..32 unique enum strings using 1..64 ASCII letters, digits, spaces, underscores, periods or hyphens. IDs are unique. Duplicate inputs, including contradictory expectations under different IDs, are rejected before activation. No label enters candidate generation.

Example sets are limited to 131072 canonical UTF-8 bytes. Imported JSON/review files are at most 262144 bytes and nesting depth 16. Unknown keys, duplicate object keys, prototype-related keys, floats/decimal/exponent syntax, nonfinite values, unsafe integers and type coercions are rejected. A saved record has exactly `schema: executable-clarifications/example-review-v1`, `example_set`, `version_digest`, boolean `confirmed` and `scope: supplied-examples-only`. Resume revalidates all fields and the SHA-256 of the entire typed set, including ordered rows and expected booleans. It detects inconsistent edits, not coherent forgery or authenticity. Pending records can be saved, but assertions and candidate audit require explicit confirmation.

Python uses `ExampleSet(spec)` from `executable_clarifications.examples`. Inspect `export_record()`, then explicitly call `confirm()`, `render_contract(example_set, 'implementation:decide')`, or `audit(reviewed_policy)`. `ExampleSet.from_record(record)` strictly resumes a saved review. The API copies its inputs and exported records. A changed set creates a new pending object. Browser typed edits likewise disable assertion export until review and confirmation. Field renaming preserves Tab and Shift+Tab order, type selections keep keyboard focus, and keyboard row removal returns focus to an enabled control. The original reviewed set remains separately downloadable during editing/import preview; cancel restores it. An imported saved review is previewed before activation and preserves exact record/export bytes.

The browser known-example export accepts an explicit `module:function` target, for example `billing.policy:eligible`. Use at most 256 ASCII characters. Each dot-separated module component and the function name must start with a letter or underscore and continue with letters, digits or underscores. Python keywords, whitespace, paths, expressions and dotted function names are rejected. Invalid targets block export. The default is `implementation:decide` in each new or reloaded tab. Changing the target during an edit cannot enable export before confirmation; cancelling the draft retains the chosen target and the original review. Importing or saving review JSON does not save or restore the target. The target changes only the known-example contract, never labels, confirmation, review digests, candidate audits or policy/integer exports. The browser never imports or runs it.

The CLI accepts `--examples FILE --confirm-examples` or `--resume REVIEW.json`, with `--save-session NEW.json` and `--target implementation:decide --export-test NEW.py`. Confirmation is explicit; `--examples` alone remains pending. `--audit-policy FILE` checks a separately reviewed policy only after confirmation. Policy answers, labels, undo and suggestions cannot be mixed with example sets. All example output paths are distinct and exclusive; validation, audit and contract rendering precede any writes. The CLI never imports the implementation.

The optional audit requires byte-equivalent canonical field declarations (including enum order) and validates policy-v1 independently. It reports `CANDIDATE_FIT` or `NO_CANDIDATE_MATCH`, fitting IDs, each candidate's exact mismatch IDs and a matrix with supplied inputs/expected booleans separate from rule predictions. Both specification digests are recorded. Policy seed cases do not add truth or assertions. Audit is read-only and never alters the reviewed example record or exported contract. Candidate fit is scoped to the supplied table; completeness, human intent and independent review authenticity remain unproven.

Version 1.1.0 adds `from executable_clarifications.conflicts import explain_conflict`, called as `explain_conflict(confirmed_example_set, reviewed_policy)`. The CLI equivalent adds `--explain-conflict` to `--audit-policy FILE` and returns a separate `conflict_explanation` result. Missing audit, pending examples or incompatible fields fail before any output file is created. The `executable-clarifications/conflict-explanation-v1` report binds both digests. If an offered candidate fits, `OFFERED_CANDIDATE_FITS` lists its ID. Otherwise `NO_OFFERED_CANDIDATE_FITS` lists a deterministic deletion-minimal `core_example_ids`, a mismatched core example per candidate, and a candidate that fits the remaining core after each example is omitted. The witness fits that remaining subset, not necessarily the entire supplied table. The core is not guaranteed globally smallest, and the report never judges labels incorrect, infers intent or proves that the offered candidates are complete.

In the known-examples browser workflow, confirm all supplied labels first, then import the separately reviewed candidate policy under **Optional candidate audit**. Inspect its exact JSON and prediction matrix. Confirm that separate review, then choose **Explain candidate gap**. The visible report shows implicated confirmed inputs/booleans, per-candidate elimination reasons and omitted-example witnesses. **Download computed explanation** saves only the computed report. Saved example/policy schemas and assertion exports stay unchanged. Starting an example edit/import, replacing the candidate file or revoking candidate review hides the explanation and requires a fresh audit review. Restoring a saved example review does not restore an explanation or candidate-audit confirmation. No uploaded code is executed.

## Local browser recovery

Unsaved sessions, original revision reviews and focused typed drafts are tracked independently in page memory. Leaving/reloading warns while any remain unsaved. Reset and replacing an active policy review require explicit discard confirmation. A session download clears only that active session; a reviewed-example download clears only its confirmed review. Draft edits and previews still need applying, saving or cancelling. Cancel policy edits returns to the unchanged active session. Browser warnings provide no crash recovery or automatic storage.

Try five supplied examples opens the exact authored fixture table for explicit review and confirmation. The truth table never enters candidate generation. See [V1 stability](STABILITY.md).

Explicit CLI input paths require regular files; regular-target symlinks remain supported. FIFOs, devices and directories are rejected before reading with a generic path-free diagnostic. This applies to examples, policy, grid, resume, comparison and candidate-audit files. File size limits are unchanged.

CLI output bundles are fully rendered and UTF-8 encoded before exclusive creation at POSIX mode 0600 (or stricter under umask). A catchable creation/write/close failure attempts to remove this invocation's files while preserving the original error. Cleanup refusal or a crash can leave owned files; multi-file export is not a transaction and requires trusted parent directories. Browser downloads follow browser/OS permissions. See [stability](STABILITY.md).
